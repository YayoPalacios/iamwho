# Evaluate OIDC subject and audience conditions statically

iamwho is not a policy simulator and does not otherwise evaluate `Condition` blocks, but web-identity trust is only meaningful through its subject conditions, so for GitHub Actions trusts we evaluate `sub` and `aud` — and only those — statically, honoring operator semantics: `StringEquals` values are literal (no wildcard expansion), `StringLike` values are case-sensitive glob patterns, condition key names match case-insensitively, any broad value in a multi-value list makes the whole condition broad, and `aud` is assessed independently of `sub`. For GitHub, `aud` never changes the `sub` verdict, because any workflow can mint a `sts.amazonaws.com` token; that rule is GitHub-specific (for Cognito, `aud` is the identifying condition). When the subject condition itself cannot be evaluated — a provider without subject rules, an unrecognised operator, a custom claim template — it is reported as not evaluated rather than guessed at or scored reassuringly. An evaluated subject verdict keeps its severity even when the statement carries other condition keys; those keys are listed, not evaluated. Checking that a provider's identifying key is *present* (GitHub/EKS/generic `sub`, Cognito `aud`) is not value evaluation and applies to every provider: its absence means any token from that IdP — or, for shared IdPs like GitHub and Cognito, any tenant of it — can assume the role. Across multiple statements the worst one wins, and unevaluated keys or `Deny` statements are listed but never credited as narrowing. Results are still *potential* reach, not proven authorization.

## Considered Options

- **Key-presence only** (prior behaviour): treated `sub: "repo:*"` as restricted, so it could not tell an all-of-GitHub trust from a single-branch trust.
- **General condition evaluation**: would turn iamwho into a partial policy simulator, which is explicitly out of scope.
- **Per-provider evaluation in one step** (GitHub, EKS, Cognito): deferred; each provider has its own identifying claims and needs its own fixtures.

## Amendment: negated and `Null` subject operators (2026-11-23)

This supersedes the earlier decision to report negated operators and `Null: false` on `sub` as not evaluated (MEDIUM); `Null: true` keeps that verdict. For GitHub, a `sub` condition that uses only negated operators (`StringNotEquals`, `StringNotLike`, and their `IgnoreCase`/`IfExists`/`ForAnyValue:`/`ForAllValues:` forms) is CRITICAL. A negation admits every subject outside the set it names, so it admits all of GitHub minus a few repositories. `Null: false` on `sub` is CRITICAL too. It only asserts that the claim exists, and every GitHub token carries one, so it scopes nothing and is equivalent to having no `sub` condition. `Null: true` is the opposite: it requires the claim to be absent, which no GitHub token satisfies. It is not overbroad, but it is not a scoping iamwho evaluates either, so it is reported as not evaluated (MEDIUM). In a multi-value `Null` list the values are ORed, so a single `false` makes it CRITICAL. A `sub` condition with no string values (an empty list, a number, an object) is treated like `Null: true`: no token's `sub` can match it, so it is not overbroad, and it is reported as not evaluated (MEDIUM). When a negation or `Null: false` sits alongside a positive `sub` condition (`StringEquals`, `StringLike`), condition blocks are ANDed. The positive condition alone decides the verdict, and the negation is listed but never credited as narrowing it further, consistent with the rule for unevaluated keys. A `sub` under an operator iamwho doesn't recognise is still reported as not evaluated, including when it appears alongside a negation.

## Amendment: negated and `Null: false` identifying keys for every provider (2026-11-23)

The rule that a negated operator or `Null: false` scopes nothing applies to every provider's identifying key (GitHub, GitHub Enterprise, EKS and generic OIDC `sub`, Cognito `aud`): a key that only appears under those operators counts as absent, so EKS and generic OIDC are HIGH and Cognito is CRITICAL rather than MEDIUM not evaluated, which would pass the default gate, while `Null: true` on the identifying key stays MEDIUM, not evaluated.
